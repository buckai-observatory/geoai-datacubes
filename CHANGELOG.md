# Project history

`geoai-datacubes` grew out of work begun in 2025 by graduate students in the
School of Earth Sciences and the Department of Computer Science and
Engineering at The Ohio State University, under the direction of
Joachim Moortgat.

## Released versions

### `0.1.1` — in development

- **Fix** (`tiler`, [#11](https://github.com/buckai-observatory/geoai-datacubes/pull/11), Aswathnarayan "Ash" Radhakrishnan): `_resolve_region_specs` was using a stale absolute import `from aoi import resolve_aoi`, a leftover from the pre-package flat layout. Any call to `split_regions` with an AOI dict (as opposed to a raw bbox list) crashed with `ModuleNotFoundError`. Fixed to `from ..fetch.aoi import resolve_aoi`; adds `tests/test_tiler_regions.py` regression coverage.
- **Packaging (breaking for pip users, transparent for mamba users)** ([#12](https://github.com/buckai-observatory/geoai-datacubes/issues/12)): moved `torch`, `torchvision`, and `scikit-image` out of the core `dependencies` list and into the `[ml]` extra so the fetch-only install path stays lightweight (~2 GB saved). Users doing `pip install geoai-datacubes[ml]` are unaffected; users doing plain `pip install geoai-datacubes` who want the `LazyTileDataset` / `geotiff_to_zarr` / ML surfaces now need to add the `[ml]` extra. `preprocessing/__init__.py` gracefully substitutes friendly ImportError-raising stubs for those two names when torch is not installed, so `from geoai_datacubes.preprocessing import fuse_response_tiffs, tile_geotiff, compute_ndvi` keeps working in torch-less envs. New CI job (`minimal-install`) enforces the split as a regression guard. Motivated by @betolink's Aug 2026 JOSS review comment at openjournals/joss-reviews#11034.
- **Packaging** ([pixi](https://pixi.sh) lockfile support): added `[tool.pixi.*]` sections to `pyproject.toml` and committed a cross-platform `pixi.lock` (linux-64, osx-arm64, osx-64, win-64) so anyone can reproduce the exact env we develop and test against with `pixi install -e <env>`. Named environments (`default`, `ml`, `earthdata`, `notebooks`, `dev`, `tests`, `full`) mirror the existing pip extras; a new CI job (`pixi-locked`) installs from the frozen lockfile and runs the full test suite, catching any pyproject/lockfile drift. Existing mamba / pip / Docker install paths are unchanged. Response to @betolink's second JOSS review ask at openjournals/joss-reviews#11034.
- **UX** (`fetch`): the STAC path (`_fetch_via_stac`, used by `earthsearch` and `planetary_computer`) and the direct-HTTP path (`_fetch_via_direct_http`, used by `direct_http`) now render a `tqdm` progress bar while iterating over bands and tiles respectively. Progress bars auto-disable in non-TTY contexts (CI, `nohup`, log redirection) so nothing changes there. The pre-existing per-tile and per-band log lines are preserved via `tqdm.write`, so they stay legible whether the bar is on or off. Response to @betolink's JOSS review comment at openjournals/joss-reviews#11034.
- **Docs**: added [`docs/architecture.qmd`](docs/architecture.qmd) with two mermaid diagrams — end-to-end fetch pipeline (validate → dispatch → provider → shared reproject-and-write stages) and provider-to-mission mapping. Linked from the navbar and sidebar under "Core pipeline". Response to @betolink's mermaid-diagrams ask at openjournals/joss-reviews#11034.
- **Docs + benchmark harness**: added [`docs/performance.qmd`](docs/performance.qmd) reporting `fetch_sentinel_data` wall-time measurements across 10 configurations (3 AOI sizes × 4 provider classes), n=3 per row per machine, on two machines (Apple M-series laptop over cellular + OSU Unity HPC's `batch` partition). Plus interpretive prose on what dominates runtime (setup-bound for small AOIs, bandwidth-bound for large ones), the levers users have (resolution is quadratic, bands linear, provider choice per mission), and honest caveats about single-run variance. The harness itself ships as `smoke-tests/perf_bench.py` (12-row `all` preset, 3-row `quick` preset for iterating, `--only <substring>` filter for targeted re-runs), `smoke-tests/perf_bench.slurm` (portable SLURM wrapper with robust conda/mamba env activation), and `smoke-tests/perf_bench_agg.py` (aggregates repeat runs into min/median/max, filterable by machine). Raw JSON logs land in `smoke-tests/perf_logs/` (gitignored). Response to @betolink's Performance-checkbox ask at openjournals/joss-reviews#11034.
- **Fix** (`fetch`, `direct_http` path): `fetch_direct_http` now expands `bands=None` into `default_bands + extra_bands` from the mission profile before invoking the per-mission `tile_callback`, matching the long-standing behavior of the STAC path (`_fetch_via_stac`). Prior to this every `direct_http` mission called with defaults (e.g. `fetch_sentinel_data(mission="Hansen-GFC", bands=None, ...)`) crashed with `TypeError: 'NoneType' object is not iterable` a few frames down in the tile_callback. Surfaced by the new `perf_bench.py` harness.
- **Docs — auto-generated API reference** (response to @wood-chris JOSS review): added a full Sphinx-style API reference page tree at `docs/api/` on the Quarto site, generated from the Python docstrings via [quartodoc](https://machow.github.io/quartodoc/). Covers 67 public functions/classes across five thematic sections (Data acquisition, Pre-processing: fuse/tile/export, Band math + metadata, ML/DL helpers, Visualisation). Each function's parameter table, return type, and full docstring is rendered next to a clickable signature; the sidebar shows the whole namespace tree when browsing any API page. Linked from the main navbar (**API** button) and from the main sidebar under a new "API reference" section. The build is wired into the `Quarto docs site` GH Actions workflow (pip installs the `[dev]` extra, `quartodoc build` runs before `quarto render`); local `quarto render` also regenerates via a `pre-render` hook so the reference stays in sync with the current package code. Directly addresses @wood-chris's `Functionality documentation` checklist item and his earlier comment that "took me a while to understand the API docs".
- **Package** (`fetch/__init__.py`): also expose `validate_query` and `fetch_direct_http` at the package's top level (`from geoai_datacubes.fetch import ...`). Both were already public functions but only reachable via their sub-module paths (`fetch.aoi.validate_query`, `fetch.fetch_data.fetch_direct_http`); the top-level exposure matches the other five fetch helpers (`fetch_sentinel_data`, `fetch_earthsearch`, etc.) and lets the auto-generated API reference show them under the natural `geoai_datacubes.fetch.*` names.
- **Docs — user-facing clarifications for novice users** (response to @wood-chris JOSS review): (1) new "Two ways to use `geoai-datacubes`" section in `README.md` between "What it does" and "Install" — clarifies the intended notebook (on-ramp) vs. script/library (compose-your-own-workflow) usage paths, directly addressing @wood-chris's fundamental question about how end users are expected to interact with the package; (2) new "Who's using this" section on the Quarto landing page (`index.qmd`) with adoption context (BuckAI Observatory + broader OSU AI ecosystem: AI(x) Hub, TDAI, ICICLE) and two published-anchor examples (Hsu & Moortgat 2026 *Remote Sensing*, Chowdhury et al. 2026 *WACV*). Substantive answers to his other questions ("ML-ready features" specifics, external users) live in the accompanying JOSS-thread reply.
- **Docs — BuckAI Observatory URL sweep**: swapped six bare `https://buckai-observatory.org` references in `README.md`, `CONTRIBUTING.md`, and `index.qmd` to the official `https://ai-observatory.osu.edu` URL. Subpath links (`/buckai-hpc-handbook/`, `/buckai-open-source-handbook/`, `/resources.html`) preserved, since those resources live on the buckai-observatory.org site infrastructure.
- **Docs clarifications and fixes** (response to @wood-chris JOSS review + external contributor @goelakash's #28 / #29): (1) fixed the broken `docs/architecture.md` reference in this changelog (now `.qmd`), thanks to @goelakash for spotting; (2) fixed the broken `[..](../geoai_datacubes/main.py)` link in `docs/configuration.md` (now points at the GitHub source URL so it resolves from the Quarto site); (3) removed three broken `providers/{earthdata,earth_engine,local_files}.md` links from the "Usage rates and quotas at a glance" table in `docs/providers.md` — those provider classes ship on the `feature/earth-engine-provider` (v0.2-preview) branch, not on `main`, so they've been dropped from the table with a footnote noting they'll be re-added with proper credential-setup pages when v0.2 lands; (4) dropped the broken `docs/HPC_RUNBOOK.md` link from `docs/HPC_QUICKSTART.md` (that runbook is intentionally local-only, not published); (5) `README.md` now notes explicitly that `mamba` is a drop-in `conda` replacement and either works, so users on plain `conda` don't need to switch; (6) `notebooks/00_geoai_datacubes_tour.ipynb` now uses `CartoDB.Positron` instead of `OpenStreetMap.Mapnik` for the AOI-context basemap — OSM's Foundation tile policy blocks Python clients from their default Mapnik server, which was 403-ing for reviewers both in Colab and locally.
- **Notebook and robustness fixes** (response to @wood-chris's Oct 2026 JOSS review): (1) notebook 03 no longer crashes when the ESA-WorldCover fetch fails (the mask is skipped and reported); the DEM and WorldCover cells in notebook 00 now fail soft like the other fetch cells; (2) `_resolve_pc_href` retries HTTP 429 and 5xx responses from the Planetary Computer signing endpoint with exponential backoff, honouring `Retry-After`; (3) new `geoai_datacubes.viz.add_basemap` replaces the inline basemap code in notebook 00. It defaults to OpenStreetMap with an identifying `User-Agent`, which OSM's tile policy requires (this supersedes the CARTO switch described above), and offers CARTO as an option that needs a free API key (`api_key=` or `CARTO_API_KEY`); (4) `geoai_datacubes.preprocessing` now loads `LazyTileDataset` and `geotiff_to_zarr` lazily, so the fetch, fuse and tile imports no longer import PyTorch even when it is installed; (5) `plot_cloud_pair` adds a legend of the Sentinel-2 SCL classes present, marking the classes that the mask removes; (6) notebook 01: the cached Random Forest is reloaded only when the installed scikit-learn version matches the one recorded next to it (otherwise it is retrained), and the cached XGBoost model is stored in XGBoost's native JSON format, which removes the unpickling version warnings; (7) notebook text: definitions of AOI, mission, band, tile, stride and data cube, a glossary for the ML terms in Section 9, explanations for the tile-count summary line, stride choice, the DEM scaling and the KMeans table, and a corrected per-city reading of the Section 10 results; (8) the Sentinel-2 L1C cell prints how to install the JP2 plugin when the driver is missing.
- **Install and CI fixes** (found while checking the pixi route for @wood-chris's environment problem): (1) `pixi.lock` had drifted from `pyproject.toml` since `quartodoc` was added to the `[dev]` extra, so `pixi install --locked` failed on `main`; the lock is regenerated (it only adds the docs-build packages) and `docs/install.md` now uses `--locked`, with a note on `--frozen`; (2) the `pixi-locked` CI job used `--frozen`, which skips the freshness check and hid the drift; it now uses `--locked` and also runs `pixi lock --check` for every environment; (3) `add_basemap` sent no key to CARTO when the installed `xyzservices` had no key placeholder in the CARTO tile URL (as in the locked environment); the key is now always appended; (4) `contextily` joins the `[dev]` extra, so CI runs the basemap tests it used to skip; (5) notebook 01 saves models it had to retrain (for example under a different scikit-learn version) to the git-ignored `notebooks/_ml_outputs/model_cache/` instead of overwriting the files shipped in git; (6) `threadpoolctl>=3.7` is now required by the `[ml]` extra and the pixi `ml` feature: with 3.6.0 in the locked environment, a `threadpool_limits(limits=1)` block followed by a single-threaded PyTorch forward pass never returned, which stalled notebook 01 (`tests/test_thread_limits.py` guards it).
- **Fix** (docs site build): the lazy loading of `LazyTileDataset` and `geotiff_to_zarr` added in the Oct 2026 review fixes made the `quartodoc build` step of the "Quarto docs site" workflow fail ("Cannot find an object named: LazyTileDataset"), so the published site was not updated after Sept 24. The two names are now also imported under `TYPE_CHECKING`, which static tools can read and which has no effect at run time; `tests/test_minimal_install.py` guards it.
- **pixi `notebooks` environment now includes the `ml` feature** (PyTorch, scikit-learn, XGBoost, scikit-image), so notebooks 00 and 01 run in it; before, it had JupyterLab but none of the ML packages, and the only environment that could run notebook 01 was `full`. `docs/install.md` now states that pixi environments are separate installs rather than layers, and that Jupyter must be started from inside an environment that contains it (`pixi run -e notebooks jupyter lab`), because a `pixi shell` of an environment without JupyterLab falls through to a Jupyter installed elsewhere, whose kernel then lacks the environment's packages. Prompted by @wood-chris's Oct 21 report on openjournals/joss-reviews#11034.
- **Environment diagnostics** (response to @wood-chris's Oct 23 report on openjournals/joss-reviews#11034): (1) the lazy `LazyTileDataset` / `geotiff_to_zarr` loader blamed a missing PyTorch for any import failure in `lazy_dataset`; it now raises the real error unless PyTorch itself is missing, and includes the original error in the hint (test added); (2) notebook 03 reports which missions failed to fetch, draws "not fetched" panels instead of crashing on a missing Sentinel-1 or DEM band, and gives a clear error when the NAIP scene needed by `segment_water` is missing; (3) the first code cell of notebooks 00, 01 and 03 prints the kernel's Python path with a note on what to do if it is not the installed environment; (4) `docs/install.md` gains two troubleshooting entries, for the macOS `OMP: Error #15` duplicate-`libomp` abort and for "installed but import fails" kernel mismatches; (5) a developer's private environment name that had leaked into notebook 00's export cell, two kernelspec names and the smoke-test scripts is replaced by `geoai-cubes`.

- **Docs** (response to @wood-chris, Oct 23): "data cube" and "fused cube" are now defined next to each other in notebook 00 (key terms and Section 9), `docs/fusion.md` and the README: a fused cube is a data cube whose bands come from several missions, not a different kind of object. The export cell of notebook 00 no longer lists `mamba install -n geoai-cubes ...` lines for zarr and lmdb, which are core dependencies and already present in any local install; only the Colab `pip` lines remain.
- **Fix** (pixi): the task `jupyter` (= `jupyter lab`) shadowed the `jupyter` executable, and `pixi run` appends arguments to a task's command, so the documented `pixi run -e notebooks jupyter lab` ran `jupyter lab lab` and stopped with "No such file or directory: .../lab". The task is renamed `lab` (`pixi run -e notebooks lab`), so the documented command now reaches JupyterLab. Found by the sanity step of the new notebooks CI job below; `tests/test_docs_ci_consistency.py` now fails if a task is named after an executable the install docs call with arguments.
- **CI runs the notebooks** (follow-up to the Oct 2026 review rounds, in which several fixes were reported as tested but had only been exercised in a long-lived development environment): a new `notebooks` workflow (`.github/workflows/notebooks.yml`) installs the locked pixi `notebooks` environment on a macOS Apple-silicon runner and executes notebooks 00 and 01 top to bottom with `smoke-tests/run_notebook.py`, which logs per-cell timing, fails on the first cell error, and verifies that the kernel is the environment's own Python; it runs on pushes and pull requests that touch the package, the notebooks or the lockfile, and weekly. `tests/test_docs_ci_consistency.py` checks that the pixi environments and commands in `docs/install.md` are the ones CI installs and runs, so the install docs and CI cannot drift apart silently again.
- **Docs** (response to @wood-chris, Oct 23): notebooks 00, 01 and 03 now say near the start that a fetch cell can fail on a timeout or an HTTP 429 from the data provider, and that running the cell again is normally enough.
- **CI runs notebook 03 weekly, in smoke mode**: a second job in the `notebooks` workflow installs the locked pixi `full` environment on a macOS runner and executes `03_with_opengeos_geoai.ipynb` top to bottom on the weekly schedule and on manual dispatch only. At full size the notebook's OmniWaterMask step did not finish in an hour on the runner's three CPU cores, so the job sets `GEOAI_DATACUBES_SMOKE=1`, which the notebook reads in its setup cell: 2-mile AOIs, a 1024 x 1024 pixel window for `segment_water` and 2 training epochs. Every cell and every call into `geoai-py` still runs. Until now notebook 03, the one that crashed for a reviewer in October 2026, had only ever been run by hand.

### `0.1.0` — 2026-06-24 — first PyPI release

- Published to PyPI as `geoai-datacubes 0.1.0` via GitHub Actions Trusted Publishing (OIDC).
- Archived at Zenodo under concept DOI `10.5281/zenodo.20829119` (version DOI for 0.1.0: `10.5281/zenodo.20829120`).
- Docker image published to `ghcr.io/buckai-observatory/geoai-datacubes` with the full `geoai-cubes` conda-forge stack plus JupyterLab.
- 26-mission catalogue: 16 direct-observation + 10 derived, spanning Sentinel-1 / 2, Landsat, NAIP, PlanetScope, MODIS, HLS, ALOS PALSAR / FNF, Copernicus DEM (GLO-30 + GLO-90), USGS 3DEP, ESA WorldCover, JRC-GSW, Hansen GFC (via new `direct_http` provider), USDA CDL, LCMAP CONUS, IO-LULC, and Chloris biomass.
- Declarative per-band `band_meta` taxonomy driving `nan_handling="auto"` and ML-ready normalisation.
- `select_bands` + `BAND_PRESETS` helper for clean hand-off to `opengeos/geoai` and other PIL-based loaders.
- Three reviewed, Colab-ready pedagogical notebooks (data-pipeline grand tour, LULC classification end-to-end, `opengeos/geoai` integration with multi-AOI held-out-city experiment) plus a fourth in-development scaffold (YOLO building detection on NAIP) kept in the repo but not part of the reviewed release.
- 85-test pytest suite on Python 3.11 + 3.12 with GitHub Actions CI.

## Timeline

- **August 2025**: Initial prototype development begun by **Bhavika Jain**
  (CSE, OSU) on the Sentinel-1 and Sentinel-2 data acquisition pipeline.
- **August – October 2025**: Iterative development of the tiling, augmentation,
  cloud-masking, NDVI computation, and LMDB / Zarr export logic in
  collaboration with **Aswathnarayan Radhakrishnan** (CSE, OSU). The
  earliest iteration of the codebase lived at
  `github.com/aswathn1/GeoDataCollection/tree/main/src/sentinel_pipeline`.
- **October 2025**: First feature-complete pipeline; Landsat support added.
- **December 2025**: Code migrated to its current home at
  `github.com/buckai-observatory/geoai-datacubes` and re-organised under
  `modules/sentinel_pipeline/` (since 2026-06-20 reorganised again into a
  proper Python package at `geoai_datacubes/`). Bhavika's commits from that migration are
  preserved in the git history.
- **December 2025 – May 2026**: Project paused due to graduate-student
  turnover.
- **May 2026 onward**: Principal investigator resumed development with major
  additions:
  - STAC-based no-credentials providers (Element 84 Earth Search,
    Microsoft Planetary Computer, Planet);
  - Copernicus DEM (GLO-30 and GLO-90) and ESA WorldCover mission profiles;
  - Smear-protected reprojection;
  - Polygon-aware Sentinel-1 same-day mosaicking;
  - Four spatially-aware train / val / test split strategies;
  - On-the-fly `LazyTileDataset` for PyTorch;
  - PlanetScope (4-band and 8-band) provider with Orders API and UDM2;
  - Mission inventory expanded to 26 user-facing missions (16
    direct-observation + 10 derived), including ALOS-PALSAR, ALOS-FNF,
    Hansen-GFC, USDA-CDL, LCMAP-CONUS, IO-LULC, Chloris-Biomass, MODIS_SR /
    MODIS_LST, HLS_S30 / HLS_L30, JRC-GSW, 3DEP, and documented stubs for
    Sentinel-5P, GEDI-L4B, and GEBCO;
  - A fifth provider class — `direct_http` — for non-STAC missions such
    as Hansen GFC's anonymous Google Cloud Storage COGs;
  - Declarative per-band `band_meta` taxonomy (`kind` + normalisation
    recipe) driving `nan_handling="auto"` and ML-ready normalisation;
  - `pyproject.toml` with optional-dependency extras (`[ml]`, `[geoai]`,
    `[notebooks]`, `[planet]`, `[dev]`, `[all]`) and a recommended
    pure-mamba install path;
  - `select_bands` / `write_label_uint8` / `BAND_PRESETS` helper for
    clean hand-off to `opengeos/geoai` and other PIL-based loaders;
  - Four pedagogical Colab-ready notebooks: the data-pipeline grand
    tour, the LULC classification end-to-end, a YOLO building-detection
    demo on NAIP, and an `opengeos/geoai` integration notebook with a
    multi-AOI held-out-city experiment;
  - Per-class LULC benchmark suite;
  - HPC quickstart and SLURM-or-bash smoke tests for every working
    mission.
